# CrewMarket 大型重构与迭代记录

## 1. 文档目的

本文件用于记录 CrewMarket 在后续改造中的核心方向、当前已知问题、拆分任务、以及每一次迭代需要补充的能力点。目标不是只记录“做了什么”，而是持续记录“为什么要做、如何验证、如何评估模型与系统表现”。

本次重构的总体目标包括：

- 让每个任务角色具备固定且可追踪的提示词与职责边界
- 在每次模型调用前后记录耗时、Token 使用量与调用结果
- 按“模块 + 角色”维度沉淀调用明细，便于最终汇总与评估
- 在 PDF 输出中加入更专业的分析层，包括风险、机会、建议与能力评估
- 为未来接入更多大模型提供统一的选择与对比入口
- 支持多段文本、多个图片等多模态输入，并可做统一汇总分析
- 将“海报生成”明确为“面向产品文案与定位的宣传海报生成”能力

## 2. 当前系统中已经识别到的关键链路

结合当前代码结构，可以看到生成链路主要分为以下几层：

## 3. 本次大型改动的任务总表

### 3.1 角色与提示词体系标准化

#### 目标
为每个任务角色建立固定提示词和职责定义，避免角色能力漂移，保证每个模型调用都能明确知道自己要承担什么任务。

#### 需要做的事
- 为所有任务角色建立统一的角色定义表
- 每个角色定义固定系统提示词、输入要求、输出格式与禁忌项
- 支持角色版本化，便于后续迭代对比
- 让角色与模块强绑定，例如：
  - 产品解析角色
  - 市场分析角色
  - 文案生成角色
  - SEO 优化角色
  - 社媒改写角色
  - 结果汇总角色
  - 海报生成角色

#### 预期效果
- 降低输出不稳定问题
- 提高多模块协作一致性
- 便于后续做模型对比与效果评测

### 3.2 模型调用前后埋点与统计

#### 目标
记录每次模型调用的时间、耗时、Token 使用量、输入输出规模、失败原因等，以便在最终评估中量化能力。

#### 需要做的事
- 在每次模型调用前记录开始时间
- 在模型返回后记录结束时间与总耗时
- 记录输入 token、输出 token、总 token
- 记录请求状态：成功、失败、超时、重试等
- 记录调用所属模块与角色
- 记录调用时使用的模型名称、版本或供应商

#### 预期效果
- 可以评估每个角色、每个模块的成本与效率
- 为模型选型提供数据支持
- 便于排查某一步骤耗时过高或 token 异常的问题

#### 前置验证（Gate）：硅基流动原始接口 usage

在 CrewAI / LiteLLM 埋点之前，先用最小探测脚本确认供应商原始响应是否带 `usage`：

```bash
py crew/probe_usage.py
```

脚本：`crew/probe_usage.py` — 直接 `POST /chat/completions`，打印 HTTP 状态、关键响应头、JSON 顶层 keys、`has_usage`、若有则打印 `usage`，以及响应体前几千字符。

| 验证项 | 结论（2026-05-30，DeepSeek-V3） |
|--------|--------------------------------|
| HTTP | 200 |
| 顶层含 `usage` | 是 |
| 字段 | `prompt_tokens`、`completion_tokens`、`total_tokens`（及 cache 相关扩展字段） |

**结论**：硅基流动 OpenAI 兼容接口**会**在 JSON 体返回 usage；token 埋点可以继续推进。

**实现**：`crew/runner.py` 在 `crew.kickoff()` 前后读取 `agent.llm._token_usage` 增量；`crew/telemetry_usage.py` 另以 patch `litellm.completion` 兜底。写入 telemetry 的 `inputTokens` / `outputTokens` / `totalTokens`。本地验证：`py crew/probe_runner_usage.py`。

## 5. 分步骤、分模块的实施原则

本次重构不采用一次性大改，而是按照“先后端、后前端”“先底层记录、后上层展示”“先单模块、后统一汇总”的方式逐步推进。每一个阶段都需要在本文件中留档，记录完成范围、影响面、验证结果和下一步待办。

### 5.1 实施原则

- 一次只改一个核心能力点，避免字段和协议同时大面积变化
- 每个模块单独验证，避免前一个模块错误影响后续判断
- 先稳定数据结构，再调整页面展示
- 所有新增字段先写入文档，再写入代码
- 所有阶段必须保留可回滚、可对比、可追踪的记录

### 5.2 推荐的分步顺序

1. 先统一角色提示词与输出格式
2. 再补齐模型调用前后 telemetry
3. 然后为每个模块建立日志与结果记录
4. 接着完善汇总分析与 PDF 报告结构
5. 再做模型选择页面与多模型接入
6. 最后升级多模态输入与海报模块定义

### 5.3 阶段性记录要求

每完成一个阶段，都需要在本文件补充以下内容：

- 本阶段目标
- 实际修改范围
- 影响到的模块
- 新增或变更的字段
- 是否影响前端展示
- 是否影响 PDF 导出
- 是否影响模型评估指标
- 验证结果
- 遗留问题
- 下一阶段建议

### 5.4 前端新增页面规划

本次前端重构需要新增两个重点页面，分别服务于“过程查看”和“模型对比”。

#### 5.4.1 模块输出与汇总页面

该页面用于展示每个模块分开输出的结果，同时提供统一汇总视图，方便查看整条链路的执行过程。

页面能力建议包括：

- 按模块拆分查看结果
- 查看每个模块的输入、输出与状态
- 查看角色级调用记录
- 查看汇总模型输出的最终报告
- 查看风险、机会和建议
- 查看 telemetry 摘要，如耗时与 token
- 支持从模块视图切换到总览视图

#### 5.4.2 多模型接入与对比页面

该页面用于管理和测试我们接入的多个大模型 API，并逐步沉淀模型优劣判断。

页面能力建议包括：

- 选择不同大模型 API
- 为不同任务角色配置默认模型
- 查看模型在不同模块中的输出效果
- 对比模型的质量、稳定性、速度和 token 成本
- 记录每次测试结果，形成模型评测历史
- 展示模型优劣标签和推荐等级
- 支持后续不断追加新的模型供应商

这两个页面都会依赖后端统一的数据结构，因此需要在后端阶段先把模块级结果、汇总结果和模型运行记录标准化。

## 9. 结构汇总评估模型（独立大模型）

### 9.1 设立目的

结构汇总不再由前置业务角色兼任，而是单独接入一个专门的 AI 大模型作为“最终汇总评估层”。这一层负责把前面所有模块的输出、过程记录、调用统计和异常信息统一整合，形成适用于前端展示和 PDF 导出的专业报告。

这样做的核心价值是：

- 前置角色只负责执行任务，不负责最终评估
- 汇总层只负责整合判断，不直接发散生成无关内容
- 方便后续替换或对比不同的大模型汇总能力
- 让最终 PDF 更像专业分析报告，而不是结果拼接

### 9.2 汇总模型的职责

汇总模型需要承担以下职责：

- 汇总各模块的核心结论
- 统一各角色的输出口径，消除重复和冲突信息
- 基于过程记录做整体质量评估
- 结合耗时、Token 消耗、失败率等 telemetry 做性能分析
- 输出风险预测、机会分析和改进建议
- 生成适合 PDF 的最终报告摘要
- 为未来的模型能力评估和横向对比提供标准化结论

### 9.3 汇总模型的输入结构

汇总模型的输入应当是一个结构化对象，而不是零散文本。建议至少包含以下几类信息：

- `taskInfo`
  - 任务名称
  - 任务目标
  - 运行 ID / request ID
  - 运行时间范围

- `userInput`
  - 原始文本输入
  - 多段文本归并结果
  - 图片输入列表
  - 图片摘要信息
  - 产品名称、品类等辅助字段

- `moduleResults`
  - 产品提取结果
  - 市场分析结果
  - 文案生成结果
  - SEO 结果
  - 社媒结果
  - 海报结果
  - 其他扩展模块结果

- `roleRuns`
  - 角色名称
  - 使用模型
  - 开始时间
  - 结束时间
  - 耗时
  - 输入 token
  - 输出 token
  - 成功 / 失败状态
  - 错误信息

- `pipelineTelemetry`
  - 总耗时
  - 总 token
  - 平均耗时
  - 成功率
  - 重试次数
  - 失败节点

- `constraints`
  - 输出要求
  - 报告风格要求
  - 风险级别标注规则
  - 是否允许推断

### 9.4 汇总模型的输出结构

汇总模型输出应当稳定、结构化、可渲染、可导出。建议输出包含以下字段：

- `executiveSummary`
  - 一段高层总结，说明本次运行整体表现

- `moduleSummary`
  - 按模块归纳每一项的核心结论

- `roleEvaluation`
  - 按角色评价其输出质量、稳定性和一致性

- `performanceReview`
  - 汇总耗时、Token、成功率、重试情况等指标

- `riskAssessment`
  - 风险点、潜在问题、失败原因、可信度不足之处

- `opportunityAnalysis`
  - 可进一步优化的方向、可扩展机会、可增强模块

- `recommendations`
  - 面向下一轮改进的建议，要求可执行

- `pdfHighlights`
  - 适合直接放入 PDF 首页或摘要页的亮点句

- `confidence`
  - 对汇总结论的置信度或稳定性判断

- `missingInfo`
  - 说明哪些信息不足，哪些结论需要补充验证

### 9.5 汇总模型的提示词模板

汇总模型的提示词应当比普通业务角色更严格，核心要点是：只基于已有结果进行综合评估，不要重新编造事实，不要脱离输入范围。

```text
你是 CrewMarket 的最终汇总评估模型。你的任务不是重新执行业务，而是基于已经提供的各模块结果、角色输出、过程日志和调用统计，生成一份专业、结构化、适合导出 PDF 的最终评估报告。

你的职责：
1. 汇总所有模块的核心结果，消除重复和冲突。
2. 基于 telemetry 数据评估本次运行的效率、稳定性和成本。
3. 输出风险预测、机会分析和可执行建议。
4. 对每个模块和角色的表现做简要评价。
5. 生成适合管理者、评审者阅读的专业化摘要。

你的约束：
- 只能基于输入内容进行总结，不得编造未提供的信息。
- 如果信息不足，必须明确指出缺失项。
- 不要输出无意义的空泛结论。
- 不要把执行任务的职责和评估职责混在一起。
- 输出必须结构清晰，适合直接用于前端展示和 PDF 渲染。

你的输出结构必须包含：
- executiveSummary
- moduleSummary
- roleEvaluation
- performanceReview
- riskAssessment
- opportunityAnalysis
- recommendations
- pdfHighlights
- confidence
- missingInfo
```

## 8. 角色提示词标准模板（建议优先落地）

下面的提示词框架用于后续每个任务角色的统一改造。实际使用时，每个角色都应在此模板基础上补充自己的业务约束与输出字段。

### 8.1 通用系统提示词模板

```text
你是 CrewMarket 中的「{role_name}」角色，职责是完成 {task_goal}。

你的工作原则：
1. 只基于输入内容和已知上下文做判断，不要编造不存在的信息。
2. 严格遵守当前角色职责，不要输出其他角色的内容。
3. 输出必须结构清晰，便于后续汇总、评估和 PDF 导出。
4. 如果输入信息不足，必须明确指出缺失项，并给出建议补充内容。
5. 优先使用简洁、可执行、可比较的表达，不要输出空泛套话。
6. 如需引用图片或多段文本内容，先整合再分析，不要遗漏关键上下文。

输出要求：
- 按照约定格式输出，不要额外夹带无关说明。
- 如果上层要求 JSON，请严格返回 JSON。
- 如果上层要求分段文本，请保持固定标题顺序。
- 必须包含风险、机会、建议或其他约定的评估字段。
```

### 8.2 角色模板补充字段

每个角色在正式接入前，建议额外定义以下字段：

- `roleId`：角色唯一标识
- `roleName`：角色名称
- `systemPrompt`：系统提示词
- `taskPromptTemplate`：任务提示词模板
- `inputContract`：输入约束，说明能接收什么数据
- `outputContract`：输出约束，说明必须返回什么字段
- `modelPreference`：默认模型或模型优先级
- `version`：提示词版本号
- `telemetryTag`：统计标签，用于日志和 PDF 汇总
